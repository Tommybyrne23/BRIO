# P02 v1 — Freeze the smallest viable BRIO product contracts

Read P00 in `output/pdf/BRIO-Manus-PWA-Playbook.md`, `docs/manus/state.md`, the five P01 audit reports, `Wireframe.md`, `brand.md`, both AGENTS files, and the attached `/home/ubuntu/upload/daily_signal_schema_v1_1.sql`. Work on branch `manus/brio-hackathon-20260912`. Preserve Better Auth, `/api/auth/**`, all three `/api/health-samples` POST payload forms, `/api/chat` NDJSON, existing worker deployment, and the Expo helper's absolute API usage.

Define shared Zod v4 runtime contracts under `code/brioweb/lib/contracts/` that are serializable and import no server-only database modules. Include profile preferences, signal consent, metric/source status, daily check-in, manual log, training session/set ledger, bounded decision, decision response event, dashboard, export envelope, and deterministic demo state. Exactly five decision actions are valid: Progress, Maintain, Repeat, Reduce, Escalate.

Contracts must distinguish `live`, `manual`, `synthetic_input`, `simulated_decision`, and `unavailable`; distinguish metric states `above`, `within`, `below`, `missing`, `excluded`, `stale`, and `insufficient`; and make value nullable rather than coercing missing to zero. Carry source, capture time, evidence window, freshness, coverage/confidence, baseline sentence, quality reason, consent version, schema/policy versions, stable client mutation IDs, and optimistic revision where applicable. Use UTC timestamps and IANA timezone identifiers with Europe/Dublin as the default.

Preferences require timezone, goal, training block, usage mode, confirmed restrictions, and onboarding completion. Consent requires each decision input signal, purpose, source attribution, default-off enabled state, changedAt, and a monotonic consentVersion, plus a separate server-AI processing signal. Daily check-in has exactly five 1–5 anchored items in this order: fatigue, muscle soreness, sleep quality, stress, mood. Manual logs allow only entered fields, distinguish nutrition intake from active energy, and validate finite non-negative quantities.

Training sessions require stable exercise/set IDs, warm-up/working type, load, reps, optional RPE, completion state, rest timer timestamps, revision, and mutation ID. Define an idempotent projection contract into existing workouts. Decisions require status, data mode, one allowed action, bounded editable proposal, evidence references, exclusions, uncertainty, concise specialist summaries, policy rule/reason, consentVersion, generatedAt, and separate accept/override events. Escalate blocks generated sessions. Preserve original recommendation after response.

Map each wireframe read/write to a proposed authenticated route under `/api/preferences`, `/api/consent`, `/api/dashboard`, `/api/check-ins`, `/api/manual-logs`, `/api/training/sessions`, `/api/decisions`, `/api/source-status`, `/api/export`, and `/api/account`, or document a deliberate equivalent. Derive ownership only from the server session. Record table ownership and migration intent in `docs/manus/contracts.md`. Treat the supplied DailySignal/RawRecord design as provenance/status guidance while retaining `health_samples` as the existing ingest store; do not create an unneeded duplicate canonical system before the demo.

Add contract tests using Node's built-in test runner, a minimal existing-compatible runner, or another lightweight harness without broad dependency churn. Include invalid finite values, reversed dates, unsupported actions/units, empty IDs, overlarge batches, default-off consent, invalid transitions, and unknown-versus-zero examples. Update `docs/manus/state.md`, `coverage.md`, `decisions.md`, and `test-results.md`. Write `docs/manus/prompts/P03-v1.md` from actual schema names and test results, including the verified P0 external-ID collision fix. No database mutation belongs in P02.
